# dtd-sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A cron Worker that keeps Double the Donation (DTD) and Monday in step both ways, pairs employer matches to the gifts they matched, writes a per-fiscal-year program summary, and shows match results in the member portal.

**Architecture:** New `dtd-sync/` Worker in the house shape (cron-only, no routes): an hourly run does pull (DTD → Monday) then push (Monday → DTD) then pairing; a nightly run writes the program summary. D1 holds the watermark, the last DTD record seen per donation, and the push ledger. `member-portal` reads the new Donations/People columns; it never calls DTD.

**Tech Stack:** TypeScript, Cloudflare Workers (cron triggers, D1, KV write-switch flags, `MONDAY_AUTH` service binding), Vitest + `@cloudflare/vitest-plugin`, Monday GraphQL API `2026-07`, DTD REST API v1.

**Spec:** [`docs/superpowers/specs/2026-11-03-dtd-sync-design.md`](../specs/2026-11-03-dtd-sync-design.md)

## Global Constraints

- Shape and tooling copied from `donation-rollups/`: same `package.json` scripts and versions, `tsconfig.json`, `vitest.config.ts`, `test/apply-migrations.ts`, `test/jsonc.ts`, `wrangler.jsonc` layout with a fully restated `env.sandbox`.
- Copy verbatim, don't re-derive: `src/environment.ts` and `src/monday/graphql.ts` from `donation-rollups/src/`, and `src/flags.ts` from `member-portal/src/flags.ts` (the canonical copy `scripts/check-worker-flags.mjs` enforces).
- Worker name `dtd-sync`; deployed names `svbc-dtd-sync` / `svbc-dtd-sync-sandbox`; D1 `svbc-dtd-sync` / `svbc-dtd-sync-sandbox`; flag key `dtd-sync-writes`.
- DTD base URL `https://doublethedonation.com/api/360matchpro/v1/`; private key is the Worker secret `DTD_PRIVATE_KEY`, sent as the `key` query parameter. It must never appear in a log line, an error message, a D1 row, or a test fixture that looks real.
- `register_donation` `donation_identifier` = `monday-<itemId>`.
- Never write People → Employer. Never overwrite a Match pairing value of `Staff`.
- Never send to DTD: Gift Type `Matching Donation`, `Sponsorship`, `Grant`, `Contract`, `Membership`; any item with a Funraise ID or a Benevity Transaction ID; Anonymous Donor checked; Status other than `Received`; Amount ≤ 0; Donor without an email. Send Gift Type `Donation` and `Event Ticket` (full Amount). Both lists live in config.
- Sandbox never emits to a vendor's production account: in `config/sandbox.json` push is limited to `push.allowEmails` (staff test addresses); `null` there means "send nothing". Production uses `"*"`. DTD has no sandbox, so this is the only guard.
- Unknown DTD status keywords are stored verbatim and mapped to the label `Other`, never an error.
- Public repo: fixtures use invented names and `example.org` emails; no `console.*` that could print an email (`node scripts/check-log-safety.mjs` passes).
- Commits: conventional (`feat(dtd-sync): …`), ending with the `Co-Authored-By` line.

## Review Focus

1. **A DTD record for a gift Monday doesn't have** (pre-migration Salesforce Opportunity, a deleted item, a Funraise gift funraise-sync hasn't written yet): logged in D1 as unmatched and retried next run; never creates an item, never fails the run. → Task 6 test `pull leaves unmatched records for the next run`.
2. **The same gift reaching DTD twice** (Funraise gift that also lacks a Funraise ID on Monday because funraise-sync stamped late; a push retried after a timeout): the ledger makes a push happen once; an item whose DTD record already arrived via pull (any `source`) is never pushed. → Task 7 tests `skips items DTD already knows` and `a failed push is retried, a recorded push is not`.
3. **Sandbox pushes reaching real donors**: sandbox People are copies of real people. → Task 7 test `sandbox sends only allow-listed emails`.
4. **DTD access stops** (401/403 because the Standard plan loses API access, or the key is rotated): the run fails loudly with a message naming the key problem (not the key), and writes nothing partial. → Task 3 test `auth failure raises DtdAuthError without the key in the message`.
5. **A match with no clear original** (two same-company gifts in the window, or none): stays unlinked, Match pairing = `Needs review`; a staff link is respected on every later run. → Task 8 tests.
