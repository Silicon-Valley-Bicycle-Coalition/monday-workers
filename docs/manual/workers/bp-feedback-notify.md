# bp-feedback-notify

[Appendix A](../reference/bp-feedback-notify.md) lists this Worker's routes, crons, queues, storage and bindings.

Deployed as `svbc-bp-feedback-notify` (production) and `svbc-bp-feedback-notify-sandbox`
(sandbox). It has no custom hostname: a Monday automation calls it on
`https://svbc-bp-feedback-notify.svbc-account.workers.dev`. It reads Monday through the
`monday-auth` broker's `SyncToken` entrypoint (the Staff sync OAuth app) and sends email through a
Cloudflare `send_email` binding.

## What it does

When Bike Parking staff mark a booked event as ready for feedback on the **BP Request Form**
board, this Worker emails the event's organizer a link to the Organizer Feedback Form. If it
stops, organizers simply don't get the survey link; nothing else depends on it.

## Trigger and data flow

One route, called by a Monday board automation. No queue, no cron.

| Trigger | What it does |
|---|---|
| `POST /webhook/bp-feedback?secret=…` | Monday "When a status changes to something, send a webhook" automation. Also accepts the secret as an `X-Webhook-Secret` header |

1. Staff set the item's **Post-Event Feedback** status to **Ready to Send**.
2. The automation POSTs to the Worker. Before real traffic, Monday sends a one-off
   `{"challenge": …}` that the Worker echoes back.
3. The Worker checks the secret, then reads only `itemId` from the body. Any other field the
   automation sends is ignored.
4. It reads the item from Monday: the organizer address from **Preferred Email Address For
   Coordination**, the event name from **Event Name** (or the item name if blank). An item not on
   the configured board gets 404; an item without exactly one valid address gets 422.
5. It claims the item in D1 table `sends` (one atomic upsert). An item emailed within
   `resendCooldownHours` (24) is not sent again.
6. With `sendStatus` configured, it also skips the send if the status column already reads
   **Sent to Organizer**.
7. It sends the email (from `fromAddress`, `fromName` and `feedbackFormUrl` in config) and
   answers the webhook.
8. In the background (`waitUntil`, 10-second timeout) it writes **Sent to Organizer** or **Send
   Failed** back to the status column. A failed send deletes its D1 claim so a retry can go out.

Because there is no queue, Monday's own webhook retries are the only retry. Monday gives up after
its retry window.

## Monday boards and columns

Board and column ids live in `config/production.json` (production) and `config/sandbox.json`. This
Worker uses `production.json`, not `svbc.json`.

| Board | Column | Access |
|---|---|---|
| BP Request Form | Preferred Email Address For Coordination | Read |
| BP Request Form | Event Name (falls back to item name) | Read |
| BP Request Form | Post-Event Feedback (status) | Read and write (`sendStatus`) |

**Post-Event Feedback** labels: `Not Yet` (default), `Ready to Send` (the automation trigger),
`Sent to Organizer`, and `Send Failed`. Writing `Sent to Organizer` doesn't re-fire the automation,
which triggers only on `Ready to Send`.

All four labels exist on the production column (`Send Failed` added 2026-11-19). Don't rename or
delete them: Monday rejects an unknown label and the Worker only logs the rejection, so a failed send
would stay invisible on the board.

The sandbox config points at board `18441421707`, "BP Request Form (sandbox)", in the CRM Sandbox v4
workspace, with the live board's ids for the two columns the Worker reads. Its feedback form's
responses go to "Organizer Feedback Form (sandbox)", `18441421727`. Don't replace it with a duplicate
of the live board: a duplicate keeps live automations, the production webhook included (see the
README). The sandbox board has no webhook automation until someone adds it in the Monday UI. A
`bp-feedback-no-email` log for an item that has an address means the column ids are wrong.

Changing the board's structure takes board ownership; without it, the `+` column button does
nothing.

## Secrets

| Name | Purpose | Issued by | Rotate |
|---|---|---|---|
| `WEBHOOK_SECRET` | `?secret=` on the automation's webhook URL. Anyone holding it can trigger feedback email for any item | Generated by the operator (`openssl rand -hex 32`) | `wrangler secret put WEBHOOK_SECRET` (`--env sandbox` for sandbox), then edit the URL in the board automation |
| `MONDAY_API_TOKEN` (optional) | Fallback Monday token from the OAuth cutover. The `MONDAY_AUTH` binding is preferred | Monday (SVBC Integration user) | Delete once the binding is confirmed. Don't add new uses |

`SANDBOX_EMAIL_SINK` is a plain var on the sandbox, not a secret. With neither `MONDAY_AUTH` nor
`MONDAY_API_TOKEN`, the Worker logs `bp-feedback-misconfigured`, answers 500 and sends nothing.

The secret appears in request URLs in Cloudflare logs. Restrict log access the same way you
restrict the secret. See [accounts and access](../03-accounts-and-access.md).

## Write switch

Key `bp-feedback-notify:writes`. It gates the send and the status write-back. The challenge echo
always works.

| Mode | Behavior |
|---|---|
| `on` | Sends normally. |
| `hold` / `unknown` | Answers **503**, sends nothing. Monday retries until its retry window ends. A request fired during a long hold may need re-triggering by hand (set the column back to `Ready to Send`). |
| `off` | Logs a masked skip line, answers 200, sends nothing and writes nothing back. |

See [Operations](../07-operations.md).

## Failure modes

| Symptom | Cause | What to do |
|---|---|---|
| Automation connection fails at setup | Worker not deployed yet, or URL wrong; the challenge handshake needs a live URL | Deploy first, then paste the URL |
| Webhook answers 401 | Secret in the URL doesn't match `WEBHOOK_SECRET` | Fix the URL in the automation, or rotate |
| Every send answers 503 | D1 unreadable, `DB` binding missing, or migrations not applied (fails closed); or the switch is `hold` | Apply migrations (see Changing it); check `node scripts/flags.mjs status` |
| 500, log `bp-feedback-misconfigured` | No Monday access configured | Check the `MONDAY_AUTH` binding and the broker |
| 502 | Monday item read failed | Monday retries; check Monday status and the broker |
| 422, item set to Send Failed | Organizer address missing or not a single valid address | Fix the address on the item, set the column back to `Ready to Send` |
| 404 | Item isn't on the configured board | Check `board.boardId` in config |
| 200 `alreadySent: true`, log `bp-feedback-resend-cooldown` | Item emailed in the last 24 hours | Wait, or delete the D1 row (see Operator scripts) |
| 200 `alreadySent: true`, log `bp-feedback-already-sent` | Column already reads Sent to Organizer | Set the column back to `Ready to Send` |
| Send fails with "destination address is not a verified address" (sandbox) | Cloudflare requires each `send_email` destination to be verified once per account | Verify the address under Email Service → Email Routing → Destination Addresses |
| Send logged `bp-feedback-send-failed` | Email Sending error | Check the sending domain in Cloudflare; re-trigger from the board |

Every send logs `bp-feedback-sent` or `bp-feedback-send-failed` with the item id, recipients
redacted.

## Operator scripts

No scripts. Operator actions:

- Allow a resend inside the cooldown:

  ```sh
  npx wrangler d1 execute svbc-bp-feedback-notify --remote --command \
    "DELETE FROM sends WHERE item_id = <itemId>"
  ```

  Sandbox: `svbc-bp-feedback-notify-sandbox` with `--env sandbox`.
- Set the write switch: `node scripts/flags.mjs bp-feedback-notify writes on --env production`.

## Changing it

Key files:

- `src/index.ts`: the route, secret check, send flow and background write-back.
- `src/feedbackItem.ts`, `src/mondayApi.ts`: the Monday item read. This Worker carries no copy of
  the shared GraphQL transport; `mondayApi.ts` has its own `tokenProviderFor`.
- `src/sendGuard.ts`, `migrations/0001_create_sends.sql`: the resend guard.
- `src/sendStatus.ts`: write-back. Set `sendStatus` to `null` in config to turn it off.
- `src/email/`: the branded layout (`layout.ts` is a copy; the root README's "Branded email
  template" names the source of truth) and the sandbox recipient rewrite (`sandboxBinding.ts`).

The sandbox `EMAIL` binding can deliver only to the sandbox mailbox, enforced by Cloudflare
(`allowed_destination_addresses`) and again in code.

Test and deploy from `bp-feedback-notify/`:

```sh
npm test
npm run typecheck
npm run deploy             # production: emails real organizers
npm run deploy:sandbox
npx wrangler d1 migrations apply svbc-bp-feedback-notify --remote
npx wrangler d1 migrations apply svbc-bp-feedback-notify-sandbox --remote --env sandbox
```

A deploy without a `database_id` auto-provisions a database but doesn't apply migrations, so
every send answers 503 until you apply them. Local dev has no broker; put a `MONDAY_API_TOKEN` in
`.dev.vars`. See [Development](../05-development.md) and [CI and deploy](../06-ci-and-deploy.md).
